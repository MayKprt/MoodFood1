# Future merchant application integration

The merchant dashboard is deliberately outside this customer MVP. A separate app can share the PostgreSQL schema and add a trusted merchant API without changing the customer decision flow.

1. Authenticate merchant users and authorize membership through `restaurant_members`. Keep merchant management behind a server boundary; current customer roles have no merchant/internal write grants.
2. Import menus into normalized dishes, options, ingredient/allergen links, availability, schedules, images, and stock. AI-generated attributes stay `source='ai_draft'` until a merchant verifies them. Customer APIs must expose only verified dietary claims.
3. Replace the customer demo catalog with a catalog repository querying eligible merchant records. Require published dishes, current schedules, valid delivery quotes, merchant availability, known prices/options, and verified safety information. Signature dishes can enter discovery but receive no guaranteed ranking boost.
4. Replace the filesystem order repository with a trusted transactional checkout service. Revalidate the entire cart and address, compute fees/taxes, record accepted totals and recipe/price snapshots, and create an order with unique `(customer_id,idempotency_key)` plus a payload fingerprint.
5. Use `reserve_order_inventory(order_id)` from a trusted worker/service role. It locks the order, merchant, dishes, and stock, validates every line before reservation, locks dish IDs in stable order, and reserves each line once. Paused merchants, unavailable dishes, missing inventory configuration, uncertain stock, and untracked stock requiring review return `needs_attention`. An untracked merchant must explicitly choose `auto_accept` to qualify. The function returns an outcome; a worker should persist attention events and notifications. Implement cancellation release, inventory consumption, and expiry before production.
6. Insert order events with unique source event IDs to prevent duplicate processing. Use a transactional outbox for notifications, Stripe work, and delivery dispatch; do not rely on browser callbacks for payment confirmation or fulfillment.
7. Implement `PaymentProvider` using Stripe payment intents and signed webhooks, with amounts computed server-side. Do not accept raw card data or redirect-based success claims as payment evidence.
8. Implement `DeliveryProvider` or extend it to async quote/dispatch/status operations. Keep courier IDs and delivery events separate from kitchen state. Verify webhook signatures, source IDs, timestamps, and ownership. Show unknown estimates honestly.
9. Add merchant RLS policies, onboarding state, notification controls, and analytics authorization in dedicated migrations. Never grant a merchant broad access to customer addresses or other merchants' orders. Expose delivery data only as needed for accepted orders.

Before switching from demo to production, validate live Supabase RLS/auth, payment authorization/capture/refund behavior, atomic concurrent stock updates, delivery callbacks, scheduling/timezones, merchant verification, support workflows, consent/privacy handling, and multi-instance order persistence.
